# First CUDA run on an NVIDIA GPU (Colab T4, 2026-10-30)

This is the first time the CUDA backend has executed. Raw logs, solver outputs and
the cell sources are in
[`validation/results/colab_t4/`](../../../../validation/results/colab_t4/).

**Result.** The CUDA build, the GPU-presence test, every tolerance-based
CPU/CUDA parity test, the benchmarks and the mixing-elbow CLI run work on a
Tesla T4. The fast suite has **3 failing cases (20 assertions)**. Every failure
is a *bitwise* CPU==CUDA equality check, and the cause is floating-point
contraction: nvcc fuses `a*b+c` into FMA by default, while the CPU oracle built
by GCC for baseline x86-64 never does. Rebuilding CUDA with `--fmad=false`, with
no source change, makes the full fast suite pass (165/165 cases, 7,338,837
assertions). This run found no defect in the CUDA kernels. `CMakeLists.txt`
now builds CUDA with `--fmad=false`; that build has not yet run on a GPU again.

The slow V1–V4 and Couette tier gives the same outcome as the M4 Pro record:
6/7 cases pass. The only failure is the six retained V2-tet wall-load order
gates (3 on CPU, 3 on CUDA), and CUDA's measured orders match Metal's within 1.5e-5.
The mixing elbow runs 23× faster on the T4 than on Colab's serial CPU, with
wall forces agreeing to ≤ 1.1e-5 relative.

### The three failures

All three compare a CUDA result with the CPU result using `==` on floats.

1. **`FV momentum face interpolation is affine exact with unequal diagonals`**:
   `tests/fv/test_flow_kernels.cpp:33`, `CHECK(got==baseline)`, CUDA versus CPU face
   values. The per-face accuracy check on line 31 (`Approx(...).epsilon(1e-6)`)
   and all other assertions in the case pass. 1 failed assertion.
2. **`FV SIMPLEC preserves rest and uniform inlet outlet flow`**:
   `tests/fv/test_steady.cpp:46`, `CHECK(u==baseline)`. It failed for 1 of the 3
   `through` cases (the log does not say which). The physical checks pass:
   `u == Approx(through).epsilon(1e-5)`, `|v| < 1e-6`, `|p| < 1e-6`, and
   continuity below 1e-6. 1 failed assertion.
3. **`CPU and Metal solves have identical iteration counts residuals and solutions`**
   (despite its name, this case runs on every available backend):
   `tests/linalg/test_solvers.cpp:528` (`final_residual ==`) and `:529` (solution
   vector `==`). These failed for 9 of the 10 (matrix, solver) combinations.
   **Iteration counts and initial residuals were identical in every
   combination**, and every solve converged. 18 failed assertions. The final
   residuals, CUDA versus CPU, in log order:

   | # | CUDA | CPU |
   | ---: | ---: | ---: |
   | 1 | 4.00236e-05 | 4.00719e-05 |
   | 2 | 4.6113e-07 | 7.3234e-07 |
   | 3 | 8.02909e-05 | 8.00267e-05 |
   | 4 | 3.11823e-07 | 4.86827e-07 |
   | 5 | 1.86542e-04 | 1.86606e-04 |
   | 6 | 3.65546e-05 | 3.6554e-05 |

### Cause: FMA contraction differs between the CPU oracle and nvcc

Evidence (`fma_probe.log`, `tests_parity_nofmad.log`, `tests_fast_nofmad.log`):

- **Toggle experiment.** The same source built with `-DCMAKE_CUDA_FLAGS=--fmad=false`
  passes all three cases (2,236/2,236 assertions) and the whole fast suite
  (165/165). No other flag differs (`CMakeCache` excerpts in `fma_probe.log`).
- **Compiler probes on `float f(a,b,c){return a*b+c;}`:**
  nvcc 13.0.88 for sm_75 emits `FFMA` by default and `FMUL`+`FADD` with
  `--fmad=false`. GCC 13.3 `-O3` (Colab) for x86-64 emits `mulss`+`addss`: no FMA,
  because the baseline ISA has none and the build adds no `-march`/`-mfma`.
  Apple clang 21 `-O3` for arm64 emits `fmadd`, because clang's default
  `-ffp-contract=on` fuses within an expression and arm64 always has FMA.
- **Why this never showed up on the Mac:** there, both the CPU oracle (clang
  contraction) and Metal contract. Metal is compiled with `MTLMathModeSafe`, and
  its bitwise equality with the CPU in the existing suite shows its contraction
  matches clang's for these kernels (inferred from passing tests, not inspected
  in the Metal IR). The independent `bench_linalg` numbers agree: CUDA on the T4
  reproduces the M4 Pro's CPU *and* Metal relative residuals to all printed
  digits (64³ PCG-Jacobi 6.83041863e-07, 128³ PCG-Jacobi 7.16956407e-07,
  64³ AMG-PCG 7.86701091e-07), while the Colab x86 CPU gives 6.85768115e-07,
  7.17042009e-07 and 7.91394974e-07. **With `--fmad=false`, CUDA reproduces
  the Colab CPU's values exactly** on all six cases (6.85768115e-07,
  7.91394974e-07, 7.17042009e-07, 8.66568009e-07, 1.53025686e-06,
  1.51536251e-06; `bench_linalg_nofmad_cuda.log`).

So the bitwise "CPU == every backend" contract holds only when the CPU oracle
and the device compiler make identical contraction choices. That depends on the
host compiler and ISA, not on Kutta's kernels. By the same reasoning the Windows
RTX artifact (MSVC, which does not contract by default under `/fp:precise`, plus
nvcc's default `--fmad=true`) should hit the same three failures. That is an
inference; it has not been run.

**Cost of `--fmad=false` on the T4 (same session, same source):**

| Measure | default | `--fmad=false` |
| --- | ---: | ---: |
| `bench_fv` CUDA outer iterations/s | 4.6395, rerun 4.8068 | 4.6497 |
| Synchronized FV kernels, ms/outer | 27.65, rerun 27.68 | 27.58 |
| `bench_linalg` 128³ AMG-PCG solve | 215.02 ms | 215.49 ms |
| `bench_linalg` 128³ PCG-Jacobi solve | 1,002.09 ms | 1,030.96 ms |
| `bench_bandwidth` triad / sum / dot GB/s | 258.43 / 107.46 / 144.23 | 257.40 / 107.92 / **109.15** |

The kernels are bandwidth-bound, so dropping contraction costs nothing
measurable except in the device dot reduction (−24%). The default run's first
CUDA case, 64³ PCG-Jacobi, took 170.92 ms against 83.42 ms in the CUDA-only
no-FMA run. That run came right after ~85 s of CPU-only cases, so the gap is
probably warm-up rather than FMA; this was not verified.

Options for the solver owners (no C++ was changed here):

- **Add `--fmad=false` to the CUDA flags** (a one-line CMake change). It is
  measured free apart from the dot reduction and makes the whole suite pass on
  this host. Kutta's CUDA targets are x86-64 Linux/GCC (CI container) and
  Windows/MSVC (the RTX package), and neither CPU oracle contracts, so the bitwise contract would hold there (Windows is
  inferred, not run). It would break again on a host whose C++ compiler
  contracts, e.g. aarch64 Linux with GCC's default `-ffp-contract=fast`.
- **Pin the CPU oracle's contraction explicitly** (`-ffp-contract=off` for
  GCC/Clang, plus `--fmad=false` for nvcc). This makes the oracle independent of
  the host compiler, but the Mac's Metal/CPU bitwise checks then need Metal to
  stop contracting too, which this run did not examine.
- **Compare different backends with a tolerance** in these three tests, keeping
  bitwise checks only within a backend. The physical checks beside them already
  pass.

My recommendation is the first now, since it costs nothing measurable and
restores a green suite on real NVIDIA hardware. The third is the durable fix if
more host/compiler combinations appear.

Scaled residual histories (`residuals.csv`, every 20 iterations) agree within
0.4% for velocity, k and omega through iteration 300, apart from one 7% continuity
excursion at iteration 40. Once residuals fall to the 1e-7–1e-8 floor, the runs
drift apart: at iteration 600 the CUDA/CPU ratios are 3.2× for continuity
(3.37e-5 vs 1.04e-5), 2.2–6.0× for the velocity components (~3e-8 vs ~1e-7),
and within 3% for k and omega. The forces above, which are what the run
reports, agree to ≤ 1.1e-5. A floor-level drift like this is consistent with
the FMA-level arithmetic differences above; this run does not separate it from
other sources of non-associativity. Both runs' `summary.json`, `forces.csv` and `residuals.csv`
are kept; `result.vtu` (13.5 MB each) was not brought back.
