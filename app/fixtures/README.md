# Fixture CLI data

`kutta-fixture` (app/tools/kutta-fixture) speaks the same protocol as the
`kutta` CLI from this data, so the app, its tests and CI run without a solver
build or Fluent case files. The real CLI always takes precedence when the app
can find one; every fixture result is labelled FIXTURE REPLAY or SYNTHETIC.

Recorded cases, each real `kutta` output captured by
`app/scripts/capture_fixtures.py` (on an M4 Pro with Metal; local paths
replaced by file names):

- `cases/mixing_elbow/`: the Ansys mixing elbow (MIT): SST, Coupled, 3D.
  `inspect*.json.qz` are the CLI's inventory (9,857 settings, with the
  Methods panel, pressure-velocity coupling and convergence criteria),
  `progress-*.jsonl` its event streams (convergence checking off),
  `run-cold` and `run-seeded` the finished runs' outputs, wall loads and views
  (without and with the Fluent data file), `live/iter-*` three live surface
  snapshots, `rejected.jsonl` the CLI's refusal without the opt-in.
- `cases/elbow_param/`: the Ansys elbow_param example: standard k-epsilon,
  SIMPLE, two approximations; its view has the app's default slice. Recorded
  with SIMPLE's paired state, so its momentum residuals reach about 2e-9.
- `cases/cylinder_tutorial/`: the Ansys adjoint cylinder tutorial: laminar
  2D, the reverse-flow approximation.
- `cases/naca4412_ground/`: a 2D ground-effect wing generated by
  `tools/fsae_aero/naca_ground_case.py` (inverted NACA 4412 over a moving
  ground; settings from the mixing elbow example): SST with the Intermittency
  Transition Model, drag and downforce reports. Its summary counts 4 cells
  under poor mesh numerics (`poor_quality_cells`).

`cases/naca4412_ground/new-case.json` is `kutta new-case --json` on the
wing's mesh (`naca_ground_case.py --write msh`). The fixture serves it for any
`naca4412_ground.msh`, applying `--speed` and `--role` as the FSAE template
does, with the CLI's notes that follow the roles (no inlet, no outlet,
stationary wheels). For `fsae_car*.msh` it builds the reply from the
synthetic car's zones with the CLI's suggestion rules, so a 3D starter with
wheels exists without a recording. A Kutta case replays its mesh's recording
(or the synthetic car). `convert` copies a Kutta case and writes the changes
it knows into it, where the real CLI writes them: reference values, the
operating pressure, and a velocity inlet's speed, turbulence intensity and
viscosity ratio. Inspecting a Kutta case reads those back over the
recording's inventory (Fluent's defaults where the case leaves them out), so
Save Case round-trips them. Other changes are refused by name; only the real
CLI writes them.

`mixing_elbow` was recorded at `868f478`; the other three at `e308968`.

The 2D views keep only the extrusion cap the app shows. Replay changes
nothing when settings are overridden; the run says so. With convergence
checking on, the replay stops where the recorded residuals and reports meet
the app's criteria; its summary, done event and wall loads then give the
replay's iteration count, while the values stay the recording's final ones
(the provenance names the recording's length). Recordings have no volume snapshot, so streamlines,
iso-surfaces and line probes need the real CLI; sections and surface
integrals work from the surfaces, and a recorded view keeps its recorded
slices.
- `fsae_car*`: synthetic, generated in code (`SyntheticCar.cpp`), to exercise
  external-aero screens and the 10M-triangle viewport benchmark. Nothing about
  it is a CFD result.
- `devices-*.json`: device inventories for macOS and an RTX Windows machine.

`.qz` files are `qCompress`ed to keep the repository small.
